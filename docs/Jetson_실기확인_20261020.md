# 2026-10-20 저녁 Jetson 확인 및 차량 적용 순서

소프트웨어 패치와 실제 장치 연결 확인은 별개입니다. 이 작업에서는 장치에 접속·설치하지 않았습니다.
아래 명령은 장치의 터미널에서 실행하는 점검 절차입니다. 정차·주행 보조 해제·오프로드에서만
설치/주소 변경/서비스 재시작/케이블 탈착을 시험하세요.

## 1. Jetson만 집에 가져온 경우 — 먼저 부팅과 기존 기능 확인

```sh
date -Is
hostnamectl
uname -a
cat /etc/nv_tegra_release
uptime
ip -br link
ip -br -4 addr
lsusb
lsusb -t
systemctl status nexo-jetlink-server nexo-jetson-hud nexo-yolo --no-pager -l
systemctl cat nexo-jetlink-server nexo-jetson-hud nexo-yolo
journalctl -b -u nexo-jetlink-server -u nexo-jetson-hud -u nexo-yolo --no-pager -n 160
ss -ltnp | grep -E ':5599|:5600|:7000'
pgrep -af 'native_host|jetson_status_beacon|orin_yolo|yolo_worker|tools.jetson.hud'
```

예상: L4T/JetPack 버전과 정상 uptime이 나오고, 필요한 서비스가 설치돼 있어야 합니다.
NCM용 서버의 실제 실행 인수는 `--transport tcp --host 192.168.100.250 --port 5599`여야 합니다.
5600 웹 포트가 없다는 이유만으로 5599 추론 서버가 고장이라고 판단하지 마세요.
YOLO는 선택된 실행 경로 하나만 동작하고 HUD도 renderer 잠금 소유자 하나여야 합니다.
서비스 이름이 없으면 설치 상태부터 확인해야 하며 임의로 프로세스를 모두 종료하지 마세요.

TURZX가 연결돼 있으면 `lsusb`에 기존 `1cbe:0092` 또는 `1cbe:0123`가 보이는지 확인합니다.
comma가 없으면 NCM NIC/peer 주소가 없거나 server가 연결 대기인 것은 자연스럽습니다.
HUD도 유효한 comma snapshot이 없으면 기다릴 수 있습니다. 이 상태로 차량 연결 성공을 확인할 수는 없습니다.

기존 저장소가 있다면 설치 위치와 로컬 수정부터 확인하세요.

```sh
cd ~/NEXOdriveXPlus  # 실제 설치 경로가 다르면 바꾸세요.
git rev-parse HEAD
git branch --show-current
git status --short
sha256sum openpilot/selfdrive/modeld/models/driving_supercombo.onnx
PYTHONPATH="$PWD" python3 openpilot/selfdrive/modeld/jetlink/diagnose_usb_owner.py --role jetson
```

기준 모델 SHA: `f73a9e535523d5e9acb9e642c64e33d631825dc8ba74123757d107cedd047bb5`.
파일 크기는 60,792,584 bytes입니다. 실제 comma 모델과도 대조해야 합니다.
다르면 임의로 모델을 교체하거나 기존 엔진을 삭제하지 말고 먼저 버전 차이를 확인하세요.

## 2. comma4를 함께 연결할 수 있을 때 — USB 장치와 인터페이스 식별

배선은 comma4 USB-C → Jetson USB-A, TURZX는 Jetson의 다른 USB-A, Jetson 별도 전원입니다.
집의 일반 PC에 Jetson을 연결한 결과가 이 배선의 검증을 대신하지는 않습니다.

Jetson에서:

```sh
lsusb -t
for n in /sys/class/net/*; do
  printf '%s driver=' "$(basename "$n")"
  readlink -f "$n/device/driver"
done
ip -br -4 addr
```

예상: comma 쪽 USB network 장치에 `Driver=cdc_ncm`이 나오고 실제 NIC 이름을 식별할 수 있습니다.
`enx...`, `enp...` 등의 이름을 usb0라고 가정하지 마세요. 여러 cdc_ncm 장치가 있으면 케이블과
주소·route를 각각 대조해야 합니다. 드라이버가 `r8152`/Wi-Fi인 NIC는 이 전송 경로가 아닙니다.

comma에서:

```sh
cd /data/openpilot
git rev-parse HEAD
git branch --show-current
git status --short
cat /data/nexo_jetlink_transport 2>/dev/null
cat /data/params/d/IsOnroad /data/params/d/IsOffroad
for g in /sys/kernel/config/usb_gadget/*; do
  printf '%s UDC=' "$g"
  cat "$g/UDC"
done
for n in /sys/kernel/config/usb_gadget/*/configs/*/ncm.*/ifname; do
  printf '%s: ' "$n"
  cat "$n"
done
ip -br -4 addr
python3 openpilot/selfdrive/modeld/jetlink/diagnose_usb_owner.py --role comma
```

예상: g1은 계속 `a600000.dwc3`에 묶여 있고 ADB/NCM 기능이 남아 있습니다.
gadget NCM ifname이 실제 콤마 USB NIC입니다. `UDC=configured`, ping, SSH만으로 모델 READY를 판단하지 않습니다.
transport 파일이 없거나 `usb`이면 기존 bulk 모드입니다. 이 상태의 g1 충돌은 실제 오류이며 패치만 받아도
NCM으로 자동 전환되지는 않습니다.

## 3. 양쪽 주소·carrier·직접 경로 확인 — 먼저 읽기 전용

각 장치 터미널에서 아래 변수에는 **그 장치에서 방금 확인한 이름**을 넣습니다.

```sh
NCM_IF='실제로_확인한_이름'
ip -j -4 addr show dev "$NCM_IF"
cat "/sys/class/net/$NCM_IF/carrier"
ip -s link show dev "$NCM_IF"
```

comma:

```sh
ip -4 route get 192.168.100.250 from 192.168.100.127
ping -I "$NCM_IF" -c 4 -W 1 192.168.100.250
ip -4 neigh show dev "$NCM_IF"
```

Jetson:

```sh
ip -4 route get 192.168.100.127 from 192.168.100.250
ping -I "$NCM_IF" -c 4 -W 1 192.168.100.127
ip -4 neigh show dev "$NCM_IF"
```

필요 조건은 comma `.127/24`, Jetson `.250/24`, 각 carrier=1, 상대 route가 해당 NIC의 직접 경로이고
gateway가 없는 것입니다. `dev wlan0`, 다른 source 또는 unreachable이면 아직 NCM 준비가 아닙니다.
ping이 막혀 있어도 TCP를 별도로 볼 수 있지만 잘못된 경로를 정상으로 간주해서는 안 됩니다.

## 4. 실제 설정이 필요할 때 — 별도 적용 항목

이 작업은 IP를 자동 부여하지 않습니다. 양쪽 현재 주소가 맞으면 아래 설정을 반복하지 마세요.
주소가 없는 것이 확인됐고 별도 복구 접속을 확보한 정차 실험에서만 해당 NIC에 임시 주소를 추가합니다.

```sh
# comma의 실제 NCM NIC에서만, .127/24가 없을 때:
sudo ip link set dev "$NCM_IF" up
sudo ip addr add 192.168.100.127/24 dev "$NCM_IF"
```

```sh
# Jetson의 실제 cdc_ncm NIC에서만, .250/24가 없을 때:
sudo ip link set dev "$NCM_IF" up
sudo ip addr add 192.168.100.250/24 dev "$NCM_IF"
```

이 명령은 기존 주소나 default route를 삭제하지 않습니다. 다시 3번의 양방향 route를 확인합니다.
동일 subnet의 Wi-Fi 경로와 겹친다면 기존 default route를 지우지 말고 USB 전용 host route/profile을
별도로 검토해야 합니다. preflight는 올바른 직접 route가 확인될 때까지 실패하는 것이 정상입니다.

임시 `ip addr add`는 재부팅 후 유지되지 않을 수 있습니다. Jetson의 실제 관리자를 확인하세요.

```sh
systemctl is-active NetworkManager systemd-networkd
nmcli -f NAME,UUID,TYPE,DEVICE connection show --active
nmcli device show "$NCM_IF"
```

NetworkManager가 관리한다면 기존 USB 전용 profile의 UUID를 먼저 확인한 뒤 그 profile에만
manual `.250/24`, `ipv4.never-default=yes`, autoconnect를 검토합니다. 기존 Wi-Fi profile을 수정하거나
여러 중복 USB profile을 만들지 마세요. comma는 실제 AGNOS 네트워크 시작 구성을 확인해야 하므로
임의의 systemd/NetworkManager 파일을 이 절차에서 만들지 않습니다.
재부팅·케이블 재열거 후 주소/route가 복원되는 것이 필수입니다.
NIC 이름이 바뀌어도 새 NIC에 주소가 복원돼 있어야 이번 제한된 재탐색이 성공합니다.

## 5. 기존 41개 차량 변경을 보존한 뒤 코드 적용 검토

실제 차량 HEAD와 41개 diff는 이 작업에 제공되지 않았습니다. 먼저 해당 장치에서 다음을 보존하세요.
이 절차는 reset/pull/서비스 재시작을 하지 않습니다.

```sh
cd /data/openpilot
umask 077
backup_dir="/data/nexo-before-jetson-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
git rev-parse HEAD > "$backup_dir/HEAD.txt"
git branch --show-current > "$backup_dir/branch.txt"
git status --porcelain=v1 > "$backup_dir/status.txt"
git diff --binary --no-ext-diff > "$backup_dir/unstaged.patch"
git diff --cached --binary --no-ext-diff > "$backup_dir/staged.patch"
git ls-files --others --exclude-standard -z > "$backup_dir/untracked.list"
if [ -s "$backup_dir/untracked.list" ]; then
  tar --null -T "$backup_dir/untracked.list" -czf "$backup_dir/untracked.tar.gz"
fi
git bundle create "$backup_dir/history.bundle" --all
ls -lh "$backup_dir"
git ls-files --others --ignored --exclude-standard
```

마지막 목록의 ignored 파일 중 필요한 사용자 모델/설정/설치 파일은 별도 보존합니다.
백업은 장치 밖에도 복사하고, 원래 HEAD와 patch/untracked archive를 읽을 수 있는지 확인합니다.
Jetson 저장소와 설치된 systemd unit도 같은 원칙으로 백업하세요.

백업 후 **읽기 전용 비교**:

```sh
git fetch origin codex/jetson-usb-status-gap-20261020
git log --left-right --oneline HEAD...FETCH_HEAD
git diff --stat HEAD FETCH_HEAD
git diff HEAD FETCH_HEAD -- openpilot/selfdrive/modeld openpilot/tools/jetson openpilot/common/jetson_status.py
```

기존 수정과 겹치는 파일을 검토·보존한 별도 배포 브랜치에서 충돌을 해결해야 합니다.
현재 dirty 작업 트리에 바로 switch/pull하지 마세요. 기존 웹 git_pull 경로가 reset을 수행하는지도 확인하고,
이번 변경 전에는 사용하지 마세요. 실제 41개 diff가 없으므로 자동 병합 안전성을 여기서 확정할 수 없습니다.

## 6. 양쪽 소스와 모델을 검토 배포한 뒤 NCM opt-in

이미 설치된 서버가 bulk 모드라면 GitHub 코드 갱신만으로 systemd 인수는 바뀌지 않습니다.
기존 installer는 서비스 구성/재시작과 TensorRT 준비를 수행하므로 1~5번을 마친 오프로드에서만 실행합니다.
실제 Jetson desktop 세션의 `DISPLAY`/`XAUTHORITY`, 모델과 Python 의존성을 먼저 확인합니다.
이를 `:0` 등으로 임의 추정하지 마세요.

Jetson (실제 NCM 이름과 comma에서 검증한 SHA를 사용):

```sh
NEXO_JETLINK_TRANSPORT=ncm-tcp \
NEXO_JETLINK_USB_IFACE="$NCM_IF" \
NEXO_JETLINK_MODEL_SHA256='f73a9e535523d5e9acb9e642c64e33d631825dc8ba74123757d107cedd047bb5' \
bash openpilot/selfdrive/modeld/jetlink/install_jetson_server.sh
systemctl cat nexo-jetlink-server
ss -ltnp | grep ':5599'
```

고정 주소 `.250:5599`에만 listen해야 합니다. 모델 SHA가 실제 comma와 다르면 설치를 멈춥니다.
서버 서비스에만 CAP_NET_RAW를 부여하는 기존 설치 방식을 사용하고 일반 Python에 setcap하지 마세요.

comma (오프로드, marker가 이미 있다면 기존 disable을 먼저 수행):

```sh
PYTHONPATH="$PWD" python3 -m openpilot.selfdrive.modeld.jetlink.ncm_transport
bash openpilot/selfdrive/modeld/jetlink/nexo_jetlink_ctl.sh status
# 이미 enable 상태인 경우에만, offroad에서:
bash openpilot/selfdrive/modeld/jetlink/nexo_jetlink_ctl.sh disable
bash openpilot/selfdrive/modeld/jetlink/nexo_jetlink_ctl.sh enable-ncm-tcp
```

preflight 예상: `.250 dev 실제NCM이름 src .127`, interface bind 권한 통과.
선택은 다음 modeld 시작부터 사용합니다. 주행 중 daemon/model을 교체하지 않습니다.
기존 로컬 수정 보존·정차 배포를 마친 뒤 정상 재시작 절차로 활성화하세요.

## 7. 실제 통신 성공과 재연결 합격 기준

comma:

```sh
cat /dev/shm/nexo-jetlink.json
cat /dev/shm/nexo-jetlink-model.json
curl --noproxy '*' -s --max-time 2 http://127.0.0.1:7000/api/jetson/status
ss -lunp | grep -E ':8766|:8767|:8768'
python3 openpilot/selfdrive/carrot/server/features/tools/nexo_jetson_diag.py
```

기대 순서는 연결 대기 → USB/통신 준비 → 모델 준비 → READY → 조건 충족 시 AI 활성화입니다.
READY는 같은 NEXO 계약과 두 번의 reset warmup을 통과해야 하며 active와 구분합니다.
모든 native timestamp가 최신인지, SHA가 맞는지, `native_link.transport=ncm-tcp`인지 확인하세요.
모델 active 진입 조건과 실패 시 기존 modeld restart 정책은 그대로입니다.

비콘은 웹 수신기 공유로 표시되고 중복 listener 오류가 없어야 합니다.
비콘 `wifi`가 살아 있다는 이유로 native USB가 정상이라고 판단하지 마세요.
UDP `packets`는 수신기 시작 이후 누계이므로 `age_s`가 함께 갱신되는지 보아야 합니다.
native READY가 정상이어도 legacy YOLO 비콘은 별도 서비스/전송 경로가 필요할 수 있습니다.

정차 상태에서 한 번에 하나씩 시험합니다.

| 시험 | 합격 기준 |
|---|---|
| Jetson을 늦게 켬 | 초기 대기 후 실제 READY, 120초 초과·명시적 오류는 ERROR |
| USB 케이블 분리/재연결 | 오래된 READY 만료, native 오류 확인, 동일 모델 검증 후 재연결 |
| Jetson server 재시작 | 통신 오류가 보이고 준비/검증을 다시 거쳐 READY |
| 양쪽 재부팅 | g1/ADB 보존, 주소·직접 route 지속, listener 복구 |
| TURZX 탈착 | renderer 한 개로 복구, Jetlink 모델 세션을 불필요하게 재시작하지 않음 |
| AI+YOLO+HUD 동시 사용 | 실물 HUD와 영상, 모델/DM 연속성, 지연·온도·메모리 함께 확인 |

서버 재시작은 정차 시험에서만 `sudo systemctl restart nexo-jetlink-server`로 수행합니다.
예기치 않은 장기 ERROR는 양쪽 동시간 `journalctl -b`, `dmesg -T`, 주소/route와 7000 JSON을 보존합니다.
추론의 P50/P95/P99/최대 지연·정확도는 실제 GPU로 별도 측정해야 하며 소프트웨어 테스트가 대체하지 않습니다.

카메라 누락이 재발하면 로그의 `modelCameraGap` 이벤트에서 missing 구간, previous/current 수신 ID와
timings_ms·jetson_state/active를 함께 확인합니다. 누락을 숨기도록 동기화 임계값이나 pose 유효성을 바꾸지 마세요.

실패 시 오프로드에서 기존 `nexo_jetlink_ctl.sh disable`로 다음 시작의 로컬 경로를 선택하고 원인을 확인합니다.
g1/UDC를 해제하거나 주행 중 모델/서비스를 바꾸는 복구는 하지 않습니다.
